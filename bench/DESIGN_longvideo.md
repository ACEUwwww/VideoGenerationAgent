# 长视频生成评测框架设计

给出这个项目（竖屏短剧 Agent）与开源长视频生成 workflow 做**可比较、可复现**的评测方案。

现状：`bench/` 是接 Video-Bench 的短视频对比工具，实测只能支撑单片段、秒级的打分，且判分链路有两个已定位的缺陷（本次已修）。本文件定义在它之上继续做什么、为什么这么选、以及每一步的验收标准。

---

## 1. 为什么不能直接把 Video-Bench 用在长视频上

三条都是实测结论，不是推断。

**1.1 采样量随时长线性增长，最终撑爆单次请求**

固定 2 fps 抽帧，同一条片段拼长后实测：

| 时长 | 帧数 | 载荷@640px | 载荷@原始分辨率 |
|---:|---:|---:|---:|
| 20s | 41 | 2.5–3.2 MB | 3.6–4.8 MB |
| 62s | 123 | 7.6–9.6 MB | 10.7–14.3 MB |
| 123s | 246 | 15.2–19.2 MB | 21.5–28.5 MB |

动态维度一次调用要装**所有模型**的帧；video-text 维度每个模型要 5 轮问答，每轮都带全部帧。2 分钟片段单维度上传就约 75 MB。这不是调参能绕开的，是采样率定义出来的。

**1.2 九个维度没有一个测「长」**

全是帧级技术质量 + 文图对齐：成像、美学、时序一致、运动、色彩/物体/场景/动作一致性。长视频 workflow 之间的真实差异——跨镜头身份漂移、叙事推进、机位连续性、节奏——一个都没覆盖。

**1.3 prompt 集是给短片段写的**

`VideoBench_full.json` 419 条，字段只有 `prompt` 和 `dimension`，**没有时长、没有镜头数**。prompt 形如 `A person is marching`，全是单主体单动作。

## 2. 候选套件评估（2026-11 调研）

只读了各仓库 README 与论文页面，**没有实际跑过任何一个**。「可跑」指的是代码已发布，不代表在本机依赖下能跑通。

| 套件 | 面向 | 规模 / 时长 | 维度 | 代码 | 主要风险 |
|---|---|---|---|---|---|
| **VBench-Long**（VBench++，TPAMI 2025） | 长视频生成 | prompt 数与最短时长**官方未声明** | 先 PySceneDetect 切镜头，再 slow-fast 双分支；custom 输入支持 6 维 | 可跑 | detectron2 限 CUDA ≤12.1；与本机 CUDA 13.1 冲突 |
| **ChronoMagic-Bench**（NeurIPS 2024） | 时移/变质性变化 | 1,649 prompt + 参考视频 | MTScore（InternVideo2 对齐）、CHScore（CoTracker2 时序） | 可跑 | 需手编 flash-attn，README 锁 CUDA 11.8/12.1 |
| **MSVBench**（ACL 2026 Findings） | **多镜头**叙事 | 20 故事，136 角色图 + 276 镜头图 | 20 子指标分 4 组：视觉质量、故事对齐、视频一致性、运动质量 | 可跑 | 需 Gemini-2.5-Flash API；torch 2.4/CUDA 12.4 |
| **ViStoryBench**（CVPR 2026） | 故事可视化 | 80 故事，344 角色，中英双语 | CIDS、Prompt Align、CSD、美学、IS | 可跑 | 权重最多（7+ expert），PromptAlign 要 API key |
| **LongAV-Compass** | **分钟级音视频** | 284 用例，60–120s，4,835 镜头 | 三层 20+ 子指标：段内 / 跨段 / 全局叙事 | 可跑 | 主要是 MLLM 判分，权重轻 |
| **MSAVBench** | 多镜头音视频 | 镜头数最多 15 | 视频/音频/镜头/参考 | **未发布**（TODO 未勾） | 不可用 |
| **T2F-Bench** | 叙事长片 | 100 prompt | 五维加权 | **仅 CSV，无代码** | 纯人工打分 |
| **Video-Bench**（现用） | 短视频 | 419 prompt | 9 维 | 已 vendored | 见 §1 |

**要排除的一类**：LVBench / Video-MME / VideoEval-Pro / RTV-Bench 都是**长视频理解**评测（考 MLLM），名字带 "long video" 但用途相反，不要混。

**一条不可信数据**：网上有页面把 93+78 组 prompt、128/256 帧（约 5/10 秒）挂在 "VBench-Long" 名下，但那个页面同时混入了 LongVideoBench、Ouroboros-Diffusion、NarrLV 等多个不同工作。**不要引用。** 要确定得读 VBench++ 正文长视频章节。

## 3. 设计取向

不做"选一个现成套件接上"，因为没有一个同时覆盖「分钟级」和「多镜头叙事」。采用**分层**：

```
                    ┌─────────────────────────────────────┐
  第三层 全局叙事     │ LLM/MLLM 看全片关键帧序列 + 剧本     │  自建
                    ├─────────────────────────────────────┤
  第二层 跨段一致性   │ 身份漂移 / 场景连续性 / 转场稳定性   │ 自建 + MSVBench 参考
                    ├─────────────────────────────────────┤
  第一层 段内质量     │ 每段用 VBench-Long 的维度打分         │ 复用
                    └─────────────────────────────────────┘
```

**关键设计决定：评测的基本单位是「段」，不是「片」。**

理由不是美学偏好，是 §1.1 的实测约束。一旦按段切分，采样量不再随总时长增长，而且每个分数都有了明确的适用单位（"第 2 个镜头这段的质量"），比"整条片 3.2 分"信息量大得多。附带好处：能看出质量在第几分钟开始塌。

**以及：不追求跨套件可比的绝对分。** 三层用不同判据，分数不跨层相加。报告分层呈现，理由和现在 `report.py` 里 1-5 与 1-3 分组是一回事。

---

## 4. 三层定义

### 4.1 第一层：段内质量（复用）

**切分方式**：优先用镜头边界（本项目的 `shots[]` 已知每镜时长；对开源模型用 PySceneDetect 或 ffmpeg 场景检测）。无镜头信息时退化为固定窗口（建议 5–8 秒，与开源模型训练时长相符）。

**维度**（沿用 Video-Bench 已 vendor 的契约，不新造）：

| 维度 | 刻度 | 每段调用 |
|---|---:|---|
| `imaging_quality` | 1-5 | 每模型 1 次 |
| `aesthetic_quality` | 1-5 | 每模型 1 次 |
| `temporal_consistency` | 1-5 | 每组 1 次 |
| `motion_effects` | 1-5 | 每组 1 次 |

video-text 五维**不进第一层**：它们需要逐段对应文本，而开源 t2v 的 prompt 是整条片的。放到第三层用另一套判据。

**聚合**：段级分数按段时长加权平均得到片级。同时保留**段级序列**，报告里给出一条"分数随时长变化"的曲线——这是能看出崩塌的手段。

### 4.2 第二层：跨段一致性（自建，有现成积木）

这一层才是长视频 workflow 之间的差异所在。

| 维度 | 判据 | 现成积木 |
|---|---|---|
| **身份漂移** | 与首段锚点的人物/主体相似度 | `mcp_servers/keyframe_memory.py` 的 256 维指纹（RGB 直方图 + 去均值亮度缩略图） |
| **场景连续性** | 同景别段之间的结构相似度 | `videobench_eval.py` 的 `scene_consistency`，含 `FRAMING_GROUPS` 跨景别自动跳过 |
| **转场稳定性** | 段边界黑帧、闪烁、冻帧、重复帧 | LongAV-Compass 的 `Trans.` 定义可参考；像素级即可，不需 MLLM |
| **色彩/影调漂移** | 段间直方图余弦 | 指纹的 `hist` 分量 |

**为什么不直接用 MSVBench**：它的"视频一致性"要 GroundingDINO + InsightFace + AdaFace + Facenet 四套权重，本机 CUDA 13.1 下装起来风险高；而人脸一致性对我们这种竖屏短剧确实是关键项，但可以先用自己的指纹度量拿到 80% 的信息量。**是否引入人脸检测器作为可选增强，等第一版跑出数据后再决定。**

### 4.3 第三层：全局叙事（自建）

| 维度 | 判据 | 实现 |
|---|---|---|
| **叙事完整性** | 是否讲完一件事（有起承转合） | MLLM 看关键帧序列 + 剧本大纲，1-5 |
| **跨段因果** | 后一段是否由前一段推出，而非各说各话 | 同上，对比段间描述 |
| **节奏** | 素材密度与注意力曲线 | 结合段级 `motion_effects` 与段时长分布，给 1-5 |
| **文本对齐（全片）** | 全片是否切题 | 沿用 video-text 的 chain-of-query，但**输入是整条片的稀疏关键帧**（每段取 1–2 帧），不是 2 fps 全采样 |

第三层的输入帧数因此与**段数**成正比，不与时长成正比——2 分钟 12 段约 24 帧，与现在的设计完全不同的量级。

## 5. 判分器（本次已修的两处）

| 缺陷 | 症状 | 修法 | 验证 |
|---|---|---|---|
| 非流式调用被代理在 153s 断开 | 4 个静态调用只返回 2 个；两轮独立实验失败耗时恒为 153.0/153.8s | `Judge.complete()` 改 `stream=True` + `stream_options={"include_usage": True}` | 同批 4 个调用 **4/4 返回正文**；`imaging_quality` 耗时 310.6s → **68.6s**，`aesthetic_quality` 656.1s → **144.4s** |
| `_loose_score()` 漏真实格式 | 回复 `- video: x ,score 2, because ...` 被读成 `None` | 新增 `scores?(?![A-Za-z])\s*(?:is|:|=)?\s*(\d{1,2})`，取**最后一处**匹配；拒绝小数；保留 1-max 区间校验 | 该片段现在解析为 **2** |

**修复后的实际出分率：8 个分数位中 6 个**（修复前 4/8）。耗时合计 966.7s → 213.0s。

**指令把分数槽位示范成字母（已修）**：上游模板是 `- video: x ,because ...`，裁判会照抄那个 `x` 而不给数字。已改为要求显式整数并给出带真实数字的示例，实测出分从 6/8 提升到 **8/8**。


**新增约束（本设计）：** 判分器不再接受"整条长片 2 fps 全采样"这种输入。`build_payload()` 保持现状服务短视频，长视频走新的分段入口。

## 6. 报告结构

```
run/
  manifest.json            模型、seed、切分方式、每段时长、配置
  segments/<model>/seg_001.mp4 ...
  scores/
    layer1_<model>.csv     段级分数序列
    layer2.csv             段间一致性矩阵
    layer3.json            全局叙事
  report.md
```

`report.md` 至少包含：

1. **分层评分表**，三层分开，不跨层相加
2. **段级分数曲线**（分数 vs 片段序号），这是发现"后段崩塌"的唯一手段
3. **生成侧成本**：每模型的渲染耗时、显存峰值、帧率——长视频 workflow 的核心差异往往在这里，不只是画质
4. **未证明的事**：样本量、seed 数、人工对齐缺失

第 3 点值得单独强调：现在 `clips.json` 只记了 `elapsed_s`。长视频对比里**单位时长的生成成本**是重要指标，必须记。

## 7. 验收标准（分阶段）

| 阶段 | 内容 | 通过标准 |
|---|---|---|
| A. 判分器可信 | 本次两处修复 | 4/4 调用返回；解析率 100%；重复判分同一片段分数一致（至少 3 个片段 × 2 轮） |
| B. 分段正确 | 实现切分 + 段内打分 | 段边界与已知 `shots[]` 对齐；段时长合计 = 片长（±1 帧）；无空段 |
| C. 第二层 | 身份/场景/转场/色彩 | 用一条**已知会漂**的合成序列（第 1 段为 A，第 5 段换人）验证度量能检出；用不漂的序列验证不误报 |
| D. 第三层 | 全局叙事 | 人工看 3 条片段，与 MLLM 打分方向一致（不要求数值一致） |
| E. 端到端 | 2 模型 × 1 prompt × 2 seed × 完整三层 | 全部维度有分数；报告可读；成本可复现 |

**A 未过，B–E 全部不做。** 判分器不可信时，任何评测接入都只是在放大"缺分数的表"。

## 8. 基线与决策（已确认）

用户已定：

1. **切分粒度 = 固定窗口**。跨模型可比性优先于对齐镜头边界；镜头边界本身是被评 workflow 的一部分，不应在评测前替它处理好。首版取 5–8 秒窗口。
2. **引入人脸检测器**，作为身份漂移的可选增强（先跑一版不含检测器的指纹基线，再对照）。
3. **不接 ChronoMagic-Bench**。它测时移变质，与短剧场景无关。
4. **基线 = LongLive 1.3B 优先接入，已完成。**

### 8.1 已接入的长视频基线：LongLive-1.3B

| 项 | 值 |
|---|---|
| 架构 | Wan2.1-T2V-1.3B + autoregressive KV-cache 学生（LoRA），连续流式生成 |
| 输出 | 832×480 @ 16fps，横版（模型训练形状） |
| 渲染 | 99–115s / 5 秒片段（单 B300，含权重加载） |
| 许可 | Apache 2.0 |
| 依赖 | 独立于 diffusers 版本栈，**走子进程**（其 requirements 锁 0.31.0，本 harness 为 0.42.1） |

**与其他基线的不可比之处（必须在报告里分开写）：**

- 分辨率方向：LongLive 是 832×480 **横版**，CogVideoX 480×720、本项目 1080×1920 都是**竖版**。竖屏短剧场景下横版基线本身吃亏，这个偏差不是 LongLive 的问题。
- 生成范式：LongLive 是流式自回归连续生成，不是"一次出固定片段"。它的强项是长程一致性，在 5 秒尺度上体现不出来——**用 5 秒片段评它是不公平的**。
- 帧数语义：`num_output_frames` 是 latent 帧数，`pixel = 4×(latent−1)+1`。已修，实测 5s 请求 → 5.06s 输出。

**由此产生的评测含义**：如果最终目的是比"长视频 workflow"，3–5 秒的冒烟规模只能验证链路通不通，不能得出质量结论。真正的对比需要分钟级片段，而那正好是设计文档第 4 节分层方案要解决的问题。

---

## 9. 已知不做的事

- 不追求与任何官方 leaderboard 数字对齐（我们的裁判是豆包，不是 GPT-4o；提示词也有本地修正）。
- 不复现论文的人类偏好相关性。
- 不把三层分数合成一个总分。
- 不在本框架里做生成性能调优，只记录成本指标。
