# 分层对比研究：运行记录与证据边界

本目录是 `bench/` 之上的分层评测研究（对应 `bench/DESIGN_longvideo.md` 的设计）。
所有数字都写明来源：哪一次运行、什么身份、样本量多大。

## 1. 相对既有 bench 的三处改动

### 1.1 prompt 集从 1 条扩到 12 条，按维度分层

既有对比只用了 `A person is marching` 一条 prompt。Video-Bench 的 prompt 集
（419 条）是**单主体单动作**的（`A red bicycle`、`Alley`、`A person is marching`），
本身测不到多镜头 workflow 的任何能力。`select_prompts.py` 按维度分层取：

| 维度 | 条数 | 理由 |
| --- | ---: | --- |
| `overall_consistency` | 4 | 唯一描述**多元素场景**的一类，最接近短剧要求 |
| `action` | 2 | 有真实运动 |
| `color` | 2 | 单一属性易判 |
| `scene` | 2 | 场景构建 |
| `object_class` | 2 | 目标保真 |

索引与原文记录在 `prompts.json`，同一脚本重复运行得到同一集合。

### 1.2 分辨率对齐（已修）

`bench/backends.py` 曾把 OpenMontage 的 `resolution` 硬编码成 `720p`，而
本项目读 `ARK_VIDEO_RESOLUTION`（`.env` 为 `480p`）。实测产物：

| 路径 | 实测分辨率 | 像素量 |
| --- | --- | ---: |
| `ours`（修复前） | 480×864 | 414k |
| `openmontage_shot`（修复前） | 704×1248 | 879k |

2.1 倍的像素差会直接进入成像/美学维度。现已改为读同一变量，两侧同分辨率。

### 1.3 OpenMontage 基线从「镜头工具」换成「完整 workflow」（关键）

既有 `openmontage_shot` 只调用 OpenMontage 的 Seedance 适配器：prompt 进、片段出，
**没有编排层**。把它当作「开源 workflow」对比会高估本项目的增量。OpenMontage 仓库
自带完整七阶段流程（script → characters → scenes → props → storyboard → voice → edit），
`bench/study/om_full.py` 驱动的是这一套。

原 `bench_run/run_pipeline.py` 在 2026-11-16 跑过一次，**在第 5 步失败**：

```
stage_failed stage=5_storyboard error="HTTP 500: 请先定稿本集再拆分镜"
stage_failed stage=6_voice     error="Edge 配音失败（音色 zh-CN-XiaoxiaoNeural）"
```

根因：`generate_storyboard` 要求 `episode.status == "confirmed"`，而那个 runner
从未调用定稿接口。缺这一步，分镜数为 0，后面全部没有产物——这也解释了它为什么会
退化成只比镜头段。

## 2. 供应商侧的三个缺陷（在 bench 层绕开，不改 vendored 源码）

| 缺陷 | 现象 | 处理 |
| --- | --- | --- |
| `auto-produce` 在分镜步骤丢失自己的 job 记录 | `GET .../auto-produce` 返回 `job: null`，同时把旧 state 写回，**10 个实体图只保住 1 个** | 不用该入口，逐阶段调用文档化路由 |
| 十段式分段（10–15 秒/段）与本项目 4 秒镜头不同构 | 单集规划 **56 镜 / 176 秒**，约 4 倍于本项目 | 生成后按 `shotOrder` 裁剪到 15 镜 / 46 秒，记录裁剪动作 |
| 出片轮询会卡在 `generating` | 任务侧已 `succeeded`，本地仍 `generating` 数十分钟 | 用 `sync-video` 重新取回，实测 15/15 补齐 |
| 剪辑草稿只含创建时刻已完成的镜头 | 15 镜成片只导出 **4 段** | `action=save` 重建时间线后再 export，实测 15 段 |

这些是 OpenMontage 自身的编排缺陷，报告里作为**该 workflow 的实际可用性**记录，
而不是当作本项目的手动干预：每一项都记录了发生位置与恢复手段。

## 4. 评测口径：三层分开

| 层 | 内容 | 刻度 |
| --- | --- | --- |
| 一：段内质量 | Video-Bench 四维（成像/美学/时序/运动） | 1-5 |
| 二：跨镜一致性 | 切镜感知的镜头内指纹漂移 | 0-1 |
| 三：结构事实 | 镜头数、时长、切点、音频、字幕、成本 | 计数 |

第二层有一个本项目已经踩过两次的陷阱，`episode_eval.py` 专门处理：

1. **切镜必须实测**，不能按分镜表的 4 秒栅格分组。xfade 会吃掉重叠，实测切点在
   4.8/8.83/12.83…，按 4 秒分组会把一个镜头劈成两组。
2. **跨切点的窗口必须丢弃**（前后各 0.7 秒保护带），否则测到的是剪辑不是漂移。
3. **片头字卡必须排除**。本项目成片前 ~0.9–1.2 秒是黑底字幕卡，与第一个镜头无共同
   结构。实测未排除时 `identity_min` 被拉到 **0.369**（shot 0 的三个窗口全部 0.37），
   排除后为 **0.588**——与 README 11.8 已记录的数字一致。这条现在自动检测而不是硬编码。

## 5. 指标定义（两张纸要能对上）

三个指标名字接近但测的不是一件事，混用会让论文结论站不住。定义固定如下：

| 指标 | 测什么 | 不测什么 | 实现 |
| --- | --- | --- | --- |
| **镜头内色彩** | 同一镜头内首窗与后续窗的调色板签名一致性 | 人物是谁 | `histogram_vector` 余弦 |
| **镜头内构图** | 同一镜头内去均值亮度指纹一致性。机位、景别一动就掉 | 人物是谁 | `thumb_vector` 余弦 |
| **跨镜角色一致性** | 同一集不同镜头里是不是同一个人（脸/发型/体型/服装） | 构图、背景、打光、调色 | 本地 Qwen2.5-VL 判定 1-5 |

为什么必须拆开：实测一条镜头从背影全景推到正面特写、人物与服装完全没变，
色彩仍为 0.885，而**构图掉到 0.694**；另一条色彩 0.901、**构图 −0.071**。
若把 `min(色彩, 构图)` 笼统称为「角色一致性」，会得到「角色崩了」的错误结论。

**测到的是构图，不是人物。** 负值是合法的：`thumb_vector` 先减去均值，
结构不相关时为负，−0.2 表示布局已无共同结构，不是数值损坏。
